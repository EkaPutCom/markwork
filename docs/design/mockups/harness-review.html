Design notes
  • One worktree per card. On start, when the project is a Git repository and isolation is on, Markwork runs git worktree add -b markwork/<slug> <parent>/.markwork-worktrees/<project>/<slug> <base> and starts pi there. The worktree sits next to the project, never inside it, so pi's tools do not see sibling worktrees, and on a VPS it falls under the same daemon root as the project. The run's folder becomes the worktree, so RunQueue no longer queues cards of one project behind each other; a per-project limit replaces it.
  • The diff is read, never trusted. The review compares the worktree (committed and uncommitted, untracked included via git add -N on a throwaway index) with the merge base. Git runs through the same spawner as pi, so on a markworkd machine it is git spawned by the daemon; the daemon stays protocol-agnostic.
  • Same shape as the other reviews. The page replaces the board in the content area like a pull request (back button, file list, linked Changes/Summary/Log buttons), files can be left out like an agent batch (“Merge 5 of 6”), and nothing reaches the project folder until Merge.
  • Merge is a Git operation the user starts: commit pi's leftovers in the worktree, then merge or squash into the base in the project folder. It refuses when the project folder has uncommitted changes or the merge would conflict; then pi can be asked to update its branch, or the user opens a terminal in the worktree.
  • Comments become the reply. Line comments are collected into “Reply to pi”, which continues the same pi session in the same worktree.
  • Summary shows evidence: pi's final answer plus the commands it ran and their exit codes, read from the log. Markwork itself still runs no project commands.
  • Recorded on the card: [branch:: markwork/checkout-with-qris] next to [agent:: pi], so the run is found again after a restart even though the run status only lives in the window (and through markworkd).
  • On a VPS (scene 5), everything Git does happens on that machine; only the diff text travels.
    • git is started as a markworkd run (spawn, read its out records and exit code, then forget), so the daemon needs no new op and stays protocol-agnostic. git must be allowed by its programs/PATH.
    • The worktree folder must be inside the daemon's roots, or pi's spawn fails with cwd_not_allowed; the settings row checks it and says so.
    • Lanes: pi runs get the lane <project>/<card> and git runs no lane, so a diff never waits behind pi. The per-project limit needs a capacity per lane group in markworkd (a small Go change), so the queue keeps going while Markwork is closed.
    • No Open Folder; Open Terminal runs ssh -t host 'cd <worktree> && exec $SHELL'.
    • Runs carry branch and worktree labels, so adopt() ties a run found again after a restart to its worktree. A lost run keeps its worktree, which can still be reviewed.
    • Every worktree is a fresh checkout (dependencies are installed again), so the settings show the free disk on the machine. The Docker fake VPS needs git to test this path.
  • Not in this mockup: a side-by-side diff, syntax colors per language, binary files (listed, no diff), several harnesses on one card.
