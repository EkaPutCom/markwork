# AGENT.md

A short guide for AI agents working on this project. The full explanation (features, shortcuts, architecture, how each module works) is in [README.md](README.md); read the relevant section before changing a related module.

## Summary

The goal of Markwork: a **Markdown workspace for humans and AI agents** for Linux, macOS, and Windows, a personal workspace for notes, documents, research, plans, and tasks together with an AI agent that understands the user's working context. The current foundation is a Markdown editor with a live formatted view, `[[note]]` links between documents, kanban boards and other layouts, an inbox, a daily journal, a Home tab that summarizes what to continue, Git history and pull requests, and an AI assistant (plus an external harness that works on `[agent:: pi]` cards). The assistant reads freely and is transparent about context and tokens, but never writes by itself: file actions are a single proposal (`agent/changes.ts`) or a batch (`agent/batch.ts`) for new files, text, insertions, deletes (to the Trash), file moves, and the notes and schema of structured documents (`agent/notechanges.ts`), and they are only applied after the user presses Apply (a batch may be partial; Undo applies the reverse through the same preflight), and the Git history is only read (`agent/gittools.ts`); keep that behavior when changing `agent/` or the Assistant panel, unless the task explicitly includes adding an agent action capability. A new action capability must have a clear access boundary, a result that can be reviewed, and user approval for the actions that need it. Distinguish the development goal from the features that are already available; see the README section "Goal: Markdown workspace for humans and AI agents".

The app is **Electron**: the core (`src/`, the whole application in plain TypeScript) runs on Node in a utility process (`electron/core.ts`) and talks to the window (`electron/renderer/`, React and CodeMirror 6) over the app protocol (`docs/design/protocol.md`). Everything is bundled by **Vite**. The GTK frontend was removed on 20 October 2026; its last state is the tag `v-gtk-final`.

Language: code comments, commit messages, interface text, test names, and documentation are written in **English**. Follow that.

- `dist-electron/`, `dist-node/`, and `release/` are build output and not in git. The Electron tests run the built app, so `npm run electron:build` after a change before `node tests/electron/<name>.mjs`.
- **During development**, run `npm run test:core:node` and the Electron test files of the area you changed. **Before declaring the work finished**, run `npm test` and report the results as they are. CI runs both suites on Linux, macOS, and Windows, and `main` only takes a pull request that passes all of them.
- **The logs must be clean**, not just "0 failed": save the output to a file and read it (`grep -nE 'Error|Warning|Unhandled|Uncaught|at .*\.(js|mjs|ts):'`), not only the summary. A page error, a console error, an unhandled rejection, or a stack trace that comes from our code is a failure even when the test passed: trace it and fix the cause. Only environment noise that is not ours (e.g. GPU or D-Bus messages from Chromium under Xvfb) may remain; mention it in the report.
- A test that fails now and then (flaky) must not be counted as passing: repeat it, find the cause, and report it if it is not solved. Tests wait for what they expect (`until()`, `within()`, Playwright's `waitFor`), not a fixed time; a fixed pause is right only to show that something does *not* happen, with a comment that says so.

## markworkd (Go)

`markworkd/` is a separate Go module (standard library only, no third-party modules): a supervisor daemon that keeps agent processes running when the app is closed. The protocol and design are in `docs/design/markworkd.md`; build and run notes are in `markworkd/README.md`. It is not part of the Vite build and runs on Linux only. From `markworkd/`: `go vet ./... && go test -race ./...` (the tests start real processes and take a few seconds). Keep the daemon protocol-agnostic: it moves lines and never parses an agent's output. Agents run under per-run shims (`internal/shim`, design section 17) so they outlive the daemon; a run that still ends `lost` is offered as *Resume* on its card (`Orchestrator.resumeInterrupted`). `MARKWORKD_TEST_SHIMS=1 go test ./internal/supervisor` runs the whole supervisor suite with every agent under a shim. The TypeScript client is in `src/agent/daemon/` (pure protocol, client, reconnecting connection; descriptor links in `streamlink.ts`, implemented by `src/platform/node/links.ts`) and `src/orchestrator/daemon.ts` (the `Spawner` adapter); its tests are `tests/unit/daemon.ts`, `daemonapp.ts`, and `daemon-live.ts` (`node dist-node/run-core-node.js --only-daemon`; the live part builds the daemon with Go; with `MARKWORK_TEST_SSH` set it also runs over a real ssh, see `markworkd/contrib/docker/README.md`). The app wiring is `src/orchestrator/hub.ts` and `src/app/harness.ts`.

A card of a Git project gets its own worktree (`src/agent/worktree.ts`, branch `markwork/<slug>` next to the project in `.markwork-worktrees/`), and its result is reviewed and merged from the review page (`src/agent/worktreereview.ts`, `src/app/harnessreview.ts`, `electron/renderer/components/Review.tsx`). Git is always a `GitRunner` parameter: `runGit` here, `daemonGit()` through markworkd on another machine; keep it that way so the same code runs on both. A path from git on another machine keeps its `/`; only paths on this computer go through `platform().paths`. Merging is the only time Markwork writes to a project folder, and only after the user confirms. Tests: `node dist-node/run-core-node.js --only-worktrees` (real git) and `tests/electron/harness.mjs` (a fake agent on the board, the review, the merge).

## A change of appearance must come with a screenshot

- **Every UI change (component, layout, CSS, dialog) must be checked through a real screenshot, and then shown to the user in the conversation.** Do not declare the appearance right only from passing tests or from reading the code.
- How: drive the app with Playwright on Xvfb (the helpers in `tests/electron/support.mjs`, or a scene in `scripts/capture.mjs` run with `MARKWORK_OUT` set to the scratchpad), save the PNG to the session scratchpad directory (not the repo), open it with Read to check it (cut-off text, size, contrast, light and dark themes, a narrow window), fix what looks off, and send it to the user with SendUserFile (`display: render`) with a short note of what is visible.
- Screenshots do not go into a commit except for `docs/assets/` through `npm run docs`.

## The look of the window

- **The rules for UI are in [`docs/design/ui.md`](docs/design/ui.md)**: tokens, the text sizes, spacing, which primitive to use when, the patterns for status, empty, errors and asking, Tooltip and `title`, and the editor's content. Read it before adding or changing UI. Where it and this section differ, `ui.md` wins; how the code got there is [`docs/design/design-system.md`](docs/design/design-system.md). `scripts/ui.mjs` (in `npm run typecheck` and `npm run test:core:node`) holds every file to it, with no baseline: follow the rule, or say why on the line with `ui-allow: <reason>`.
- The window is drawn with **shadcn/ui** (Tailwind v4, Radix, the zinc theme, Geist, Lucide icons). The reference is the mockup in `docs/design/shadcn/` (four `.dc.html` artboards: the editor, the board, the Assistant in the dark theme, the command palette), and `docs/assets/` shows the app as it is. The layout: a sidebar with the workspace, Home and the journal, the panel of the page shown and the pages at its foot (closed, a rail of the same icons); a header with the sidebar toggle, the breadcrumb whose last part is the Document Menu, the Saved/Unsaved badge, the layout button, the New split button, the Assistant and the main menu; tabs centered over the editor from two documents; counts at the foot of the editor. Keep to that look; do not restyle it toward another app unless the user asks.
- shadcn/ui components live in `electron/renderer/ui/` (`components.json` names the folders; `@/` is `electron/renderer/`). Use them for new UI (Button, Badge, DropdownMenu, …) and add one with the shadcn CLI or by hand in the same shape; `cn()` is in `renderer/lib/utils.ts`. The older parts keep their own classes in `electron/renderer/styles/theme.css`, drawn as the shadcn component they are (`.button` = outline Button, `.flat` = ghost, `.suggested` = default; `.chip` = Badge; `.popover` = DropdownMenu content; `.dialog` = AlertDialog); they are being replaced by the primitives, so new code never uses them. Icons are named in `renderer/components/Icons.tsx` and drawn from Lucide.
- Colors are the theme tokens of `electron/renderer/styles/globals.css` (shadcn's `--background`, `--foreground`, `--muted`, `--primary`, … plus `--success` and `--warning`) with light and dark values; a new color is a token, never a literal in a component. theme.css stays outside the CSS layers (so it wins over CodeMirror's defaults) and names a bare element only inside `@layer base` (so it never overrides a Tailwind utility). The appearance must be right in both themes and in a narrow window (below 900 px the Assistant floats, below 600 px the side panel too; `renderer/lib/client.ts` `layoutOf`).
- A status must not be conveyed only through color or an icon: give it text or an accessible name (`aria-label`, a role), and every function must be reachable with the keyboard. The Electron tests find elements by role and name, so an inaccessible control is also an untestable one.

## A performance check is mandatory

- **Check the performance impact of every change to the application code before declaring the work finished.** Correctness tests alone are not enough.
- A change to `src/markdown/` runs `npm run bench:compare` with an equivalent size, number of repetitions, and fixture (`--fixture=long` for tens of thousands of lines, `--fixture=book` for a ±650 KB manuscript); report the median, p95, maximum, and any regression. Update `tests/bench/baseline.json` only from a complete valid result after a deliberate change, and never to hide a regression.
- The editor in the window is not covered by `npm run bench`. A change to `electron/renderer/lib/editor.ts` or its decorations is measured in the app: open `tests/samples/all-formats.md` and a long document, type, move the cursor, paste, and undo, and use Chromium's performance tools (Playwright's `page.evaluate` with `performance.now()`, or a trace). Say what was measured and what was not.
- **Every time there is a performance improvement, also update `docs/learn-performance.html`** (linked from `docs/index.html`): its commit in the journey list, a chapter with the symptom, the cause, the data structure before and after, before/after numbers, and the lesson. After changing it, open the page in a browser: no console error and no horizontal scroll at a width of 375 px.
- For a documentation-only change, state that the benchmark was not run because there is no runtime impact.

## Structure and the layer rules

```
electron/     main.ts (the window, dialogs, URL schemes, safeStorage), core.ts (the core's utility process),
              preload.ts, updater.ts, renderer/ (the page: client.ts, App.tsx, editor.ts, one component per view)
src/
  app/        the application layer: AppSession and its controllers; app/protocol/ is the app protocol (messages, the server
              and its handlers per controller, the replica of the editor's text)
  markdown/   string → data functions, pure TypeScript, imports nothing outside markdown/
  agent/      the AI assistant and the external harness (no runtime of its own; files, processes, and HTTP go through platform())
  forge/      Forgejo/Gitea pull requests: client, polling, sending changes, resolving conflicts (HTTP and git are parameters)
  platform/   the port to the runtime: index.ts is the contract, node/ implements it with Node built-ins
  base/       the base of the core: settings, settingskeys, welcome, files, fileops, workspace, git, gitlog, credentials, cancel,
              i18n, activity
  orchestrator/   index.ts runs harness processes; daemon.ts through markworkd; hub.ts is the connection per machine
tests/
  unit/       the core's tests, one file per module
  core/       core-tests.ts lists the unit tests, run-core-node.ts runs them on Node; the framework, fixtures, and test host
  electron/   the app's tests with Playwright; support.mjs is what they share
  live/       live tests against real services (DeepSeek, Forgejo)
  bench/      benchmarks, their baseline.json, and AGENTIC.md
  samples/    sample documents (used by the tests and by manual checks)
```

The direction of dependencies: the renderer → the pure parts of `src/` (and types); `electron/core.ts` → `app/protocol/` → `app/` → the core → `markdown/` and `platform/index.ts`. A lower layer never imports an upper one, and nothing in `src/` imports `electron/`. A controller in `app/` declares the views and dialogs it needs (plain data in, `on*` actions or a value/Promise out), `AppSession` builds every controller, and `app/protocol/frontend.ts` turns `AppFrontend` into messages. A new feature that needs the window goes the same way: a controller in `app/`, its messages in `app/protocol/` (a handler per controller in `handlers/`), a component in the renderer that draws and reports, and a scenario in `tests/unit/protocol.ts` and in an Electron test. What `AppFrontend` and `AppDialogs` take and return is plain data, no callbacks, `Set`, `Date`, or live objects (`tests/unit/plaindata.ts`, checked by `tsc`; its `KNOWN` list may only shrink). A controller that changes an open document's text from what it is uses `editor.update(edit)`, not `getText()` and then `replaceText()`, because a write over the protocol can land after more typing; `LaggingEditor` in `tests/unit/appsession.ts` fails a controller that reads back its own write.

### The rules that keep the core clean: do not undo them

- **Text logic is pure and shared.** Editor commands are `markdown/editcommands.ts`; the syntax parser is `markdown/highlight.ts`; inline Markdown is cut into style runs by `markdown/inlineruns.ts`, which `inlinehtml.ts` draws. A new way of showing inline text is a new drawing of `inlineRuns`; it never re-parses the Markdown with its own regular expressions, and a new Markdown behavior goes into the shared parser so every drawing gets it. The same holds for what a click means (`markdown/clicks.ts`), conflict markers (`markdown/conflicts.ts`), which code blocks are diagrams (`markdown/diagram.ts`), table column widths (`fitColumns` in `markdown/table.ts`), where an image comes from (`markdown/imagesource.ts`), and Windows path spellings (`markdown/paths.ts`). The renderer reuses these instead of copying them; `scripts/layers.mjs` lists what it may import from `src/`.
- **The runtime is behind `platform()`.** Files, paths, processes, terminals (`processes.openTerminal`), the keyring, HTTP, settings, and translations are the port in `platform/index.ts`; `platform/node/` implements it, and what differs per system lives in `platform/node/dirs.ts` and `platform/terminals.ts` as pure functions that `tests/unit/crossos.ts` runs for all three systems. Core and `app/` code never test `process.platform`, name a system's program, or build a path with `'/'` for a place on disk: use `platform().paths` (`join`, `isAbsolute`, `relative`, and `same` to find a file by its path). A `/` is right only for names inside a work folder, repo paths, URLs, and paths on another machine. The core typechecks against `src/globals.d.ts` only (timers, `TextEncoder`, `TextDecoder`), so a Node global or a `node:` import outside `platform/node/` fails.
- **Decisions live in `app/`, and the window decides nothing.** The renderer draws what it is sent and reports what the user did; a path, a token, or an answer it sends back is checked by the core against what the core offered.
- **The Markdown text is the single source of truth**, so any view can redraw a board, table, or list from it.

Run `npm run typecheck` and `npm run test:core:node` (both run `scripts/layers.mjs`) and keep them green. Never fix a failing layer check by adding an exception or moving the check; move the code instead. The exception lists may only shrink.

## Code conventions

- Imports between modules use the **`.js`** suffix even though the file is `.ts` (`import { x } from './tags.js'`).
- Indentation of 4 spaces, single quotes, semicolons. Match the style and the density of comments with the files around it; a comment explains *why*, not *what*.
- The functions in `markdown/` (including the board and table model operations) are pure: they do not change their arguments and return new values.
- The renderer keeps no application state of its own beyond what is on screen: the store in `renderer/lib/client.ts` holds what the core sent, and an action goes to the core and comes back as a notice.

## Known pitfalls

- **Text positions:** the protocol counts code points, CodeMirror and JavaScript strings count UTF-16 units (an emoji = 1 vs 2). Convert with `markdown/offsets.ts` at the editor's edge.
- **Write files through `base/files.ts`.** Autosave writes in the background (`writeTextFileAsync()`); a synchronous write, a move, and a delete of a file must call `flushWrites()` (already done by `writeTextFile()` and `fileops.ts`) so that the old contents do not overwrite the new.
- **The Assistant:** the manuscript context is built in `agent/context.ts` (pure, tested in `tests/unit/agent.ts`); keep the `system` part stable between questions (the DeepSeek prefix cache) and everything that changes goes into `note`. The browsing tools are in `agent/tools.ts` and are read-only; a new tool must be pure (working on top of `SourceFile[]`), must not throw, and must be registered in `TOOLS` and in `runTool()`/`describeCall()`. A tool that changes something lives in `agent/changes.ts` (`CHANGE_TOOLS`), only produces a pure `Change`, and is run by the session through `onProposal`, which waits for the user's decision in the review dialog; its application (`applyChange()` in `app/agentwrites.ts`) checks again that the file has not changed and that its name is safe. A proposal is an ask: the panel gets the changes as data, asks the core to write them, and the result the agent sees is what the core wrote. A new write tool follows the same pattern and gets tests in `tests/unit/changes.ts` and `tests/unit/assistant.ts`. Tests never call the real API: use a fake `Provider` (`session.assistant.chat.makeProvider`, or `MARKWORK_TEST_MODEL` for the app) and a fake `KeyStore`.
- **The external harness:** a card with `[agent:: pi]` is run by `orchestrator/index.ts` in the project folder that is mapped from the name in `settings.projects` (only filled in through the folder chooser; do not accept a path from the Markdown contents or from the agent), and `checkProjectFolder()` rejects the Markwork work folder together with its contents and parents. The pure logic (the prompt, `PiReader`, `RunQueue`) is in `agent/harness.ts` and tested in `tests/unit/harness.ts`; the app tests use a fake agent (`MARKWORK_TEST_HARNESS`, `tests/electron/agent.mjs`), never the real pi.
- **Conversation history:** `ChatController.persist()` (`agent/chatcontroller.ts`) writes to `<folder>/.markwork/chats` through `agent/chatstore.ts` (the format is in `agent/transcript.ts`). Tests use a temporary folder; do not write to the user's folders. Dot folders are not read by `WorkspaceRepository` (`base/workspace.ts`); keep that so that the assistant does not browse its own history.
- **A process that does not answer:** `runGit()` (`base/git.ts`) has a watchdog that turns a hanging git (`gitLimits.runMs`) or a lost result into an ordinary failure without repeating the command (it may have been a commit). A new long-lived subprocess or async wait gets an end that does not depend on the other side answering.
- **Workbench formats (Home, Inbox, Journal, `[[note]]` links):** an item carries typed fields as `[key:: value]` in its first line; `markdown/fields.ts` parses and writes them, and `kanban.ts` holds the one model of a board and of a list. The parsers never reject or rewrite text they do not understand. The journal's activity (`.markwork/activity/YYYY-MM-DD.jsonl`, `base/activity.ts`) is merged into the *Activity* section only by adding lines that are not there yet, so user edits are never overwritten; keep that rule. `[[note]]` targets are resolved by file name without extension, case-insensitively, against the Markdown files of the work folder.
- **Context menus** are data (`app/menu.ts`, `MenuEntry[]`); a test calls the `run()` of its entry, and the window asks the core for a card's menu and runs an entry by its token.
- **The visual editor hides Markdown, but the cursor and the keys work on the text.** A hidden range (`![alt](url)`, fences, link syntax) still has positions, so one place on screen can be several positions in the text, and some places on screen have none. That one cause was behind Enter opening a line under a picture instead of under the text, a click after the text landing between two hidden pictures, no way to get a line between two pictures or after a code block, and Backspace joining a line to a closing fence. The rules that keep them apart:
  - Every hidden piece is an atomic range (`visualEditing` in `renderer/lib/visual.ts`), and so is the whitespace between two consecutive pictures (`editor.ts`), which would otherwise be a place for the cursor that looks like the end of the text.
  - A cursor among the pictures that end a line stands before them, where it is seen; moving right with the keys goes on to the next line, a click stays (`keepOutOfPictureRuns` in `renderer/lib/blockselect.ts`).
  - A picture, a code block, or a diagram is picked as one object (`blockselect.ts`): a click on it, Esc in a code block, or Backspace/Delete right next to it picks it, with a ring and a key hint; Enter and typing start a line after it, Backspace/Delete remove it, Esc and the arrows let go, Copy/Cut take its Markdown. A new kind of drawn object joins this model through `BlockSource`; do not patch one key for one widget.
  - A key next to an object picks it before it changes anything hidden (a Backspace after a code block would join the line to its fence).
  - A single click on something drawn does not navigate or open: a link gets a tooltip with buttons, a diagram is picked and its source opens from the toolbar. Every action has a visible control (the block toolbars in `renderer/lib/blocktools.ts`), not only a double click or a modifier.
  - A deletion can make a prefix grow: removing the first letter of a heading's text ("## a b" less its "a") joins the space after it to the hidden prefix (`##  `). The cursor goes on to where the text starts now (`textStartAfter` in `visual.ts`), and `prefix-guard` also checks the cursor a deletion leaves.
  - Hidden ranges can lie inside one another (a picture's whole markup over its own `![` and `](…)`): a key steps past the one that reaches furthest (`pastHidden`), and a picture whose address cannot be told (a relative one in a text with no file) is still a picture, drawn as missing, never hidden markup with nothing shown.
  - What the visual editor hides goes into `concealed.hidden` (and a line's prefix into `concealed.prefixes`), never by another way: the keys, the cursor rules, and the Editor Inspector (`renderer/lib/inspect/`, `docs/design/debugger.md`) all read it there. A new kind of hidden range, or a new rule of the visual editor (a bug fixed is one), gets a check in `renderer/lib/inspect/checks.ts` and a step in `tests/electron/inspector.mjs`; a new `StateEffect` worth seeing in its log is named with `nameEffect`, and a new command of the visual editor that takes a key is wrapped in `traced('area.name', …)` (a DOM handler in `handling()`), with `trace()` at the decision it makes, so the log says who took the key and why. Run the app with `MARKWORK_DEV=1` and `Ctrl+Alt+I` to see the text, the transactions, and what the checks found; `npm run editor -- --headless …` gives the same as JSON, and a bug you can reproduce is saved with `save-repro` and played again with `replay`. `fuzz` presses random keys with every check and saves a shrunk repro of what fails; a bug fixed keeps its repro as a test with `test-from` (`tests/electron/repros/`, played by `tests/electron/repros.mjs`).

## Adding or changing a feature

1. A new Markdown rule → put it in `src/markdown/` and write a test in `tests/unit/`.
2. A decision → a controller in `src/app/`, tested with `AppSession` and recording views in `tests/unit/`; its messages in `src/app/protocol/` with a scenario in `tests/unit/protocol.ts`. Every test module exports one function and is registered in `tests/core/core-tests.ts`; it reaches the runtime only through `platform()` and `host()` (`disk` in `framework.ts` for test files). Use `section`, `test`, `eq`, `ok` from `tests/core/framework.ts`; a test that waits is `await test(name, async () => …)`.
3. What the window shows or does → a component in `electron/renderer/` and a step in the matching `tests/electron/*.mjs`, finding elements by role and name.
4. A new Markdown format → add its example to `tests/samples/all-formats.md` (used by the tests and the HTML export).
5. A changed feature, shortcut, or folder structure → update `README.md` (the shortcut table, the feature list, the folder tree, and the related "How it works" section) and the command in `app/commands.ts`.

## The test environment

- The core's tests use in-memory settings (`memorySettings()` in `tests/unit/appsession.ts`) and temporary folders, with `XDG_CONFIG_HOME` and `XDG_DATA_HOME` pointing into one, so the user's settings and Trash are not touched.
- Each Electron test file gets its own settings and data folder (`launchApp` in `tests/electron/support.mjs`), on every system.
- `node dist-node/run-core-node.js --only-worktrees` and `--only-daemon` run part of the core's tests for fast iteration (after `npm run test:core:node` has built them).
- Do not edit `dist-electron/`, `dist-node/`, or `node_modules/` by hand.
- **Drive the editor the way a person does.** A step that puts the cursor with `setDoc(text, pos)` only proves the position it chose, and the bugs of the visual editor come from where a click lands. For anything with hidden markup or widgets, click at what is seen (the end of a line's text, a picture, the start of a line: `textEdges` in `tests/electron/visual.mjs`) and then press the keys. Those steps found a bug the position-based ones missed.
- **What a plugin draws in a measure frame (`requestMeasure`) is not there right after the key.** Wait for it with `waitFor`, and when a change only removes something (a ring, a class), make it in the plugin's `update` at once. CI runners, Windows above all, are slower than a local run and catch a check made one frame early; the same goes for a command that needs the previous one to have settled (the table-cell Bold step waits for the toolbar to show Bold off before pressing it again).

## Git

- Commit messages are in English, one short sentence in an imperative/descriptive form, written as `type(module): description` (e.g. `fix(editor): keep the selection when a format command wraps it`). `type` is one of `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`; `module` is the area changed, such as `editor`, `kanban`, `assistant`, `home`, `journal`, `electron`, `build`, or `docs`.
- One logical change per commit; include its tests in the same commit.
- `main` is protected: changes arrive through pull requests that pass CI on all three systems.
