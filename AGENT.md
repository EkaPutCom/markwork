# AGENT.md

A short guide for AI agents working on this project. The full explanation (features, shortcuts, architecture, how each module works) is in [README.md](README.md); read the relevant section before changing a related module.

## Summary

The goal of Markwork: a **Markdown workspace for humans and AI agents** on the Linux desktop, a personal workspace for notes, documents, research, plans, and tasks together with an AI agent that understands the user's working context. The current foundation is a Markdown editor with a live formatted view, `[[note]]` links between documents, kanban boards, an inbox, a daily journal, a Home tab that summarizes what to continue, Git history, and an AI assistant (plus an external harness that works on `@pi` cards). The assistant reads freely and is transparent about context and tokens, but never writes by itself: file actions are a single proposal (`agent/changes.ts`) or a batch (`agent/batch.ts`) for new files, text, insertions, deletes (to the Trash), file moves, kanban, and the notes and schema of structured documents (`agent/notechanges.ts`), and they are only applied after the user presses Apply (a batch may be partial; Undo applies the reverse through the same preflight), and the Git history is only read (`agent/gittools.ts`); keep that behavior when changing `agent/` and `ui/chat.ts`, unless the task explicitly includes adding an agent action capability. A new action capability must have a clear access boundary, a result that can be reviewed, and user approval for the actions that need it. Distinguish the development goal from the features that are already available; see the README section "Goal: Markdown workspace for humans and AI agents". **GTK 4 + GtkSourceView 5 + GJS** (WebKitGTK 6.0 for diagrams), **TypeScript** code bundled by **Vite** into `dist/`. The app is run by GJS (SpiderMonkey 115), **not** Node.js, so Node and browser APIs are not available at runtime. Node is only for the build.

Language: code comments, commit messages, interface text, test names, and documentation are written in **English**. Follow that.

- `dist/` is the build output and is not in git. **The tests always run from `dist/`**, so rebuild before running `gjs -m dist/run-tests.js ...`.
- `npm test` needs `xvfb-run`, `Xvfb`, and `xauth`; the GUI and mouse tests use a virtual display so they do not need a desktop session and do not move the user's pointer. The GJS runner directly can still use a desktop session; without a display, use `--no-gui`.
- **During development**, use `npm test` (Xvfb, does not move the user's pointer) as the everyday test. If there is no display, at least `npm run typecheck` + `--no-gui`.
- **At the end of development**, before declaring the work finished, also run `npm run test:ui` (on a real X11 desktop; the pointer will move, so tell the user) and report the results of both commands as they are.
- **The logs of both tests must be clean**, not just "0 failed": check the output and make sure there is no `Gjs-CRITICAL`, `Gjs-WARNING`, `Gtk-WARNING`, `GLib-*`, stack trace, or any other error/warning line that comes from our code. Trace and fix the cause (often a test that uses a widget that has already been destroyed), do not hide or ignore it. Only environment warnings that are not from our code (e.g. `libEGL warning: DRI3`) may remain; mention them in the report. **You must read the full log** (not just `tail` or `grep ✓`/a pass-fail summary): save the output to a file and then `grep -nE 'CRITICAL|WARNING|Error|Traceback|Stack trace|^\s+@'`. If the log is not clean, fix it and run it again until it is clean before declaring it finished; the final report must state the result of this log check.
- **A new feature or a change of appearance must be checked through a screenshot.** Run the app (e.g. through `scripts/capture.ts` or `npm start` on Xvfb/desktop), take a screenshot of the relevant state (light and dark themes if related), then look at the image and judge whether the layout is right: the position and width of the sidebar, alignment, spacing, cut-off text, widgets that expand or overlap. Green tests alone do not prove that the appearance is right. Fix whatever looks off before declaring it finished, and mention in the report what was checked.
- A test that fails now and then (flaky) must not be counted as passing: repeat it, find the cause, and report it if it is not solved.

## markworkd (Go)

`markworkd/` is a separate Go module (standard library only, no third-party modules): a supervisor daemon that keeps agent processes running when the app is closed. The protocol and design are in `docs/design/markworkd.md`; build and run notes are in `markworkd/README.md`. It is not part of the Vite/GJS build. From `markworkd/`: `go vet ./... && go test -race ./...` (the tests start real processes and take a few seconds). Keep the daemon protocol-agnostic: it moves lines and never parses an agent's output. Agents run under per-run shims (`internal/shim`, design section 17) so they outlive the daemon; a run that still ends `lost` is offered as *Resume* on its card (`Orchestrator.resumeInterrupted`). `MARKWORKD_TEST_SHIMS=1 go test ./internal/supervisor` runs the whole supervisor suite with every agent under a shim. The TypeScript client is in `src/agent/daemon/` (pure protocol, client, reconnecting connection; descriptor links in `streamlink.ts`, implemented by `src/platform/gjs/links.ts`) and `src/orchestratordaemon.ts` (the `Spawner` adapter); its tests are `tests/unit/daemon.ts`, `tests/unit/daemonapp.ts`, and `tests/unit/daemon-live.ts` (`gjs -m dist/run-tests.js --only-daemon`; the live part builds the daemon with Go; with `MARKWORK_TEST_SSH` set it also runs over a real ssh, see `markworkd/contrib/docker/README.md`), and the GUI tests in `tests/gui/agentshost.ts` (`--only-agents`, with an in-memory stand-in daemon so no ssh is ever started; `--shot-agents=<prefix>` saves screenshots). The app wiring is `src/daemonhub.ts` and `src/window/harness.ts`.

A card of a Git project gets its own worktree (`src/agent/worktree.ts`, branch `markwork/<slug>` next to the project in `.markwork-worktrees/`), and its result is reviewed and merged from the review page (`src/agent/worktreereview.ts`, `src/ui/harnessreview.ts`, `src/window/harnessreview.ts`). Git is always a `GitRunner` parameter: `runGit` here, `daemonGit()` through markworkd on another machine; keep it that way so the same code runs on both. Merging is the only time Markwork writes to a project folder, and only after the user confirms. Tests: `gjs -m dist/run-tests.js --only-worktrees` (real git, no display) and `--only-harness` (the fake pi on the board, the review, `--shot-harness=<prefix>` saves `-review.png`); the project page in Preferences is in `--only-agents` (`--shot-agents=<prefix>` saves `-project.png`).

## A change of appearance must come with a screenshot

- **Every UI change (widget, layout, CSS/theme, window, dialog) must be checked through a real screenshot, and then shown to the user in the conversation.** Do not declare the appearance right only from passing tests or from reading the code.
- How: render the widget or its window on Xvfb with `widgetPixbuf()` (`tests/widgets.ts`) from a GUI test, save the PNG to the session scratchpad directory (not to the repo), open it yourself with Read to check it (cut-off text, size, contrast, light and dark themes), fix it if needed, and then send it to the user with SendUserFile (`display: render`) with a short note of what is visible. The existing patterns: `--screenshot=a.png` for the editor window and `--shot-proposal=<prefix>` for the agent proposal review window (see `tests/run-tests.ts` and `tests/gui/chat.ts`). For a new view, add a similar option in its test so it is easy to repeat.
- A view that cannot be rendered on Xvfb (e.g. one that depends on a GPU or a portal) is reported as not visually verified, not assumed to be right. Screenshots do not go into a commit except for `docs/assets/` through `npm run docs`.

## The UI must follow the GNOME standards

**Scope: the GTK frontend (`src/ui/`, `src/window*`, `src/editor/`).** The Electron frontend (`electron/`) is a separate design decided by the owner (19 October 2026): it is written in React and, since 19 October 2026, its look follows the GTK window (header bar, icon rail with the Files panel, centered tabs, counts at the foot, Adwaita colors and symbolic icons), not VS Code. The rules below do not apply to it; the rules for sharing logic with the core do (see "The foundation for other frontends").

- **Every Markwork interface (widget, panel, dialog, window, icon, color, text) must follow the [GNOME Human Interface Guidelines](https://developer.gnome.org/hig/) and the libadwaita idioms.** Markwork is a GNOME app (`com.ekaput.Markwork`, the GNOME 50 Flatpak runtime); an appearance that imitates a web/Electron app or another platform is not accepted even if it resembles a mockup that was given. Take the intent of the mockup, and then realize it with GNOME components.
- The order of choice: an `Adw.*` widget → a GTK 4 widget → a default Adwaita style class (`card`, `dim-label`, `heading`, `caption`, `navigation-sidebar`, `boxed-list`, ...) → your own CSS in `ui/theme.ts` only if it is not covered yet.
- Colors use the named Adwaita colors according to their role: `@success_color`/`@warning_color`/`@error_color` for text/icons, the pair `@*_bg_color` + `@*_fg_color` for a background that holds text or an icon. Icons use the standard symbolic icons (`*-symbolic`). The appearance must be right in both the light and dark themes and follow the system accent.
- A status must not be conveyed only through color or an icon: give a text or an accessible label (`accessible_role`, `update_property(Gtk.AccessibleProperty.LABEL)`), and all functions must be reachable with the keyboard.
- A libadwaita/GTK API that is newer than the installed version (1.5/4.14) is used with feature detection and a fallback path, e.g. `Adw.Spinner` (1.6+) with a `Gtk.Spinner` fallback in `ui/worklist.ts`. The details of the idioms, the deprecated widgets, and their patterns are in the section "Known pitfalls" (the items **New UI follows the GNOME idioms**, **Interface text must be translatable**, **Adaptive layout**).
- When reporting a UI change, also mention its conformance with the HIG and any deviation that was left on purpose together with the reason.

## A performance check is mandatory

- **Always check the performance impact of every change before declaring the work finished.** Correctness tests alone are not enough for a change to the application code.
- For a change to the application code, run `npm run bench:compare` and benchmark the scenarios that are affected. Compare before/after with an equivalent document size, number of repetitions, fixture kind, and environment; report the median, p95, maximum, and any regression that is found.
- A change to the editor, highlighting, or layout must be checked on a normal document and a long document. Use the `long` fixture for tens of thousands of lines, the `book` fixture (`--fixture=book --size=400 --sizes=50,200,400`, a manuscript of ±650 KB) for the book writing experience, and a document with many tables/code blocks when related. To open a document, look at `open: longest pause` (the main loop pause that feels frozen), not only the total of `setText`. Check opening the text, typing, moving the cursor, paste, delete, undo, and redo according to the scope of the change.
- Trace a meaningful regression before declaring the performance improved. If the benchmark hangs, GJS callbacks are blocked during GC, or the measurement is incomplete, report it as a failed/not verified check; do not use a partial result as a baseline or as evidence that the app is comfortable.
- Update `bench/baseline.json` only from a complete valid result after a deliberate change has been evaluated, and record the result and its limitations in `bench/PERFORMANCE.md`. Do not replace the baseline just to hide a regression.
- **Every time there is a performance improvement, also update `docs/learn-performance.html`** (linked from `docs/index.html`), the performance learning documentation for developers. Add its commit to the journey list and, if the metric is covered, to the chart data (`typeData`/`cursorData`). Write a new chapter or extend an existing one with the symptom, the cause, an illustration of the data structure before/after, before/after bars (`.cmp[data-rows]`) from the numbers in `bench/PERFORMANCE.md`, and the lesson. Add a simulation if the change to the data structure can be demonstrated; say whether that simulation is a real measurement or a calibrated model. Also record any regression that appeared in the regression section. After changing it, open that page in a browser to make sure there is no console error and no horizontal scroll at a width of 375 px.
- For a documentation-only change, still check that the runtime code did not change and state that the benchmark was not run because there is no runtime impact. If the environment prevents a needed benchmark, report the reason and the scope that has not been checked.

## Structure and the layer rules

```
src/
  markdown/   Markdown rules, pure TypeScript, WITHOUT GTK imports (easy to test)
  forge/      Forgejo/Gitea pull requests: client, polling, sending changes, resolving conflicts (no GTK; HTTP and git are parameters)
  agent/      the AI assistant: building the manuscript context and the model client (no GI; files, processes, and HTTP go through platform())
  editor/     the editor engine (MarkdownView, tags, highlighter, images, tables, code)
  ui/         standalone interface components (sidebar, kanban, dialogs, ...)
  app/        the application layer every frontend shares: feature controllers (documents, views, journal, harness, review, Home,
              collaboration, the Assistant, the git history, agent writes, autosave, note links) that see widgets only through view, dialog, and TextEditor interfaces
              (no GI, no ui/); app/session.ts (AppSession) builds and owns them from one frontend object; app/commands.ts is the
              command registry (id, label, default keys, scope, run)
  window.ts   the only place where the components are connected to each other: the GTK frontend of AppSession; implements its views,
              dialogs, and hosts on its widgets (one `MarkdownView` per tab)
  window/     the GTK glue left: the Doc type with MarkdownView, the harness log windows
  actions.ts  maps the command registry onto Gio.Actions and GTK accelerators, typing the window as `ActionHost`
  colors.ts   the document color palettes, pure data shared by editor/ and ui/
  gtkutil.ts  GTK 4 helpers usable by all layers (see Code conventions)
  files.ts, git.ts, settings.ts, activity.ts, orchestrator.ts, workspace.ts, credentials.ts, i18n.ts
              the base of the core: no GI at all, they reach the runtime through platform() (platform/index.ts)
  platform/   the port to the runtime: index.ts is the contract, gjs/ fills it with GLib, Gio, libsoup, libsecret, GSettings;
              node/ fills it with Node built-ins only (it runs the core's tests in `npm run test:core:node`)
  fileops.ts  file operations for the file tree (create, rename, move, copy in, trash), through platform(); a base module
tests/
  unit/       tests without a GUI, one file per module
  gui/        tests with a real window, one file per module
  run-tests.ts, framework.ts, fixtures.ts
  samples/    sample documents (used by the tests and by manual checks)
```

The direction of dependencies: `window.ts` → `app/*` and `window/*`, `actions.ts` → `ui/*`, `ui/*` → `app/*` (for the view and data types), `editor/*` → `markdown/*`, `agent/*`. A lower layer must not import an upper layer. `editor/` must not know about `ui/`, files, or menus; it reports through callbacks (`onHighlighted`, `onCursorMoved`, ...) that are connected in `window.ts`. Nothing imports `window.ts` except `app.ts` and tests: a controller in `app/` declares the host, view, and dialog interfaces it needs and the window fills them (`frontendHost()`, `viewScreen()`, `appDialogs()`, `documentsHost()`, handed to `AppSession`, which builds every controller), and a new feature that grows `window.ts` by more than a few methods goes into its own controller in `app/` the same way. A controller in `app/` never imports GI or `ui/`: a widget it needs becomes an interface with plain data and `on*` callbacks, and a dialog becomes a function that answers with a value or a Promise. Shared types live at the lowest layer that uses them (e.g. `Palette` in `colors.ts`, `GitRequest` in `gitlog.ts`).

Markwork is GNOME first, and the GTK frontend is the only one being built. The layering keeps a second frontend possible (Electron for macOS and Windows, if demand from those platforms grows; the path is `docs/design/electron.md`), so do not loosen these rules because only GTK uses them today. Keep the application layer shaped for a frontend in another process (`docs/design/protocol.md`, section 13.1), even though only GTK exists: a module in `ui/` does not import, for its values, a core module that reaches the runtime (git, file operations); that work goes through `app/` (`UI_ACTS_ALLOWED` in `scripts/layers.mjs` is empty and may not grow). What `AppFrontend` and `AppDialogs` take and return is plain data, no callbacks, `Set`, `Date`, or live objects such as a `Doc` (`tests/unit/plaindata.ts`, checked by `tsc`; its `KNOWN` list may only shrink). A controller that changes an open document's text from what it is uses `editor.update(edit)`, not `getText()` and then `replaceText()`, when another write may come before it in the same turn; `LaggingEditor` in `tests/unit/appsession.ts` fails a controller that reads back its own write.

### The foundation for other frontends is done: do not undo it

The layering above is finished work, not a plan. The core runs on Node (`npm run test:core:node`), `AppSession` makes every application decision, and the frontend contract is plain data, so a second frontend (Electron, a web page, a TUI) can be built without touching the core. What already exists, and what a change must keep true:

- **Text logic is pure and shared.** Editor commands are `markdown/editcommands.ts` (GTK applies them in `editor/textedit.ts`); the syntax parser is `markdown/highlight.ts` (`editor/highlighter.ts` is only the `GtkTextBuffer` adapter); inline Markdown is cut into style runs by `markdown/inlineruns.ts`, and `pango.ts` and `inlinehtml.ts` are two drawings of the same runs, as `chatmarkup.ts` and `chathtml.ts` are of `chatblocks.ts`. A new way of showing inline text is a new drawing of `inlineRuns`; it never re-parses the Markdown with its own regular expressions, and a new Markdown behavior goes into the shared parser so every drawing gets it.
- **The runtime is behind `platform()`.** Files, paths, processes, terminals (`processes.openTerminal`), the keyring, HTTP, settings, and translations are the port in `platform/index.ts`; `platform/gjs/` and `platform/node/` implement it, and what differs per system lives in `platform/node/dirs.ts` and `platform/terminals.ts` as pure functions that `tests/unit/crossos.ts` runs for all three systems. Core and `app/` code never test `process.platform`, name a GNOME program, or build a path with `'/'` for a place on disk: use `platform().paths` (`join`, `isAbsolute`, `relative`, and `same` to find a file by its path, since case and `..` parts must not make two tabs of one file). A `/` is right only for names inside a work folder, repo paths, URLs, and paths on another machine.
- **Decisions live in `app/`.** A view reports what the user did and draws what it is given; it does not decide, read files, or run Git (`UI_ACTS_ALLOWED` stays empty). What `AppFrontend`, `AppDialogs`, and the controllers' views take and return is plain data.
- **The Markdown text is the single source of truth**, so any frontend can redraw a board, table, or list from it.

Before finishing a change, ask: could Electron or a TUI reuse this without GTK? If the logic is a decision, put it in `app/`; if it is text in, data out, put it in `markdown/`; if it touches the system, add it to the port with both implementations and a test that runs on Node; only the drawing stays in `ui/`, `editor/`, or `window/`. Run `npm run test:core:node` (it also runs `scripts/layers.mjs`, which fails on a core or `app/` file that mentions `process.platform` or a system's program such as `kgx` or `secret-tool`) and keep it green. Never fix a failing layer check by adding an exception, importing `gi://` into the core, or moving the check; move the code instead. The exception lists may only shrink.

What is deliberately **not** built yet, and not to be started unless the user asks: a full Electron frontend (only an MVP exists: `electron/` and the protocol slice in `src/app/protocol/`, with documents, tabs, and the board; every other view is `unwired`) or any other second frontend, CI for macOS and Windows, and `markworkd` on macOS and Windows. The state of each gap is in `docs/design/electron.md`; update it when a change closes or opens one.

## Code conventions

- Imports between modules use the **`.js`** suffix even though the file is `.ts` (`import { x } from './tags.js'`).
- GJS modules are imported with `gi://`, e.g. `import Gtk from 'gi://Gtk?version=4.0'` (also `Gdk?version=4.0`, `GtkSource?version=5`, `WebKit?version=6.0`). The GJS built-in modules (`gi://`, `system`, `gettext`, `cairo`, `console`) are marked `external` in Vite; do not add runtime dependencies from `node_modules`.
- Indentation of 4 spaces, single quotes, semicolons. Match the style and the density of comments with the files around it; a comment explains *why*, not *what*.
- The `@girs/*` types sometimes do not match the runtime behavior (example: the XID `GdkX11.X11Surface.get_xid()` in `tests/widgets.ts`). Give a narrow cast and a short comment, do not loosen the tsconfig.
- The GTK 4 helpers are in `src/gtkutil.ts` (usable by all layers): `iterAtLine()` (GTK 4 returns `[ok, iter]`), `childrenOf()`/`removeChildren()` (there is no `get_children()`), `onClick()`/`onKeyPress()` (controllers that replace the event signals), `pack()` (replaces `pack_start`), `modal()`/`after()` (Promise-based modal dialogs without a nested main loop), `textureFromPixbuf()`/`pixbufFromTexture()` (replacements of the deprecated GTK pixbuf APIs). Use those, do not rewrite the patterns.
- The functions in `markdown/` (including the kanban and table model operations) are pure: they do not change their arguments and return new values.

## Known pitfalls

The details and the reasons are in the README, section "Technical things to know".

- **Text positions:** GtkTextBuffer counts per code point, JS strings per UTF-16 unit (an emoji = 1 vs 2). Convert with `makeCpMap()` (`markdown/offsets.ts`) right before touching the buffer.
- **Do not use the `invisible` attribute** of a GtkTextTag (it can crash GTK 3; the layout of tables/diagrams/markers relies on these small tags). Hiding text uses the `hidden` tag with the small size `TINY` = 256, **not** 1 (a size of 1 makes the emoji font fail to draw).
- **Images and tables are not buffer contents.** Both are TextView overlay widgets above empty space (`pixels_below_lines`). Do not insert a `GtkTextChildAnchor` because it pollutes the document and the undo history. Overlays **cannot be detached** in GTK 4.14 (`gtk_text_view_remove()` gives "is not a child"), so borrow a slot from `OverlaySlots` (`editor/overlays.ts`), position it with `place()` (buffer coordinates), and give it back with `release()`; attach click receivers to the contents of the slot, not to the slot. Overlays also do not scroll along without help (see the README, GTK 4 notes): `OverlaySlots` reallocates the TextView and its container every time it scrolls. An overlay position test must compare the actual position of the widget (`translate_coordinates`) after scrolling, not the number stored by the layer. Do not use `ListBox.remove_all()` (it also removes the placeholder); use `removeChildren()`.
- **The buffer text is the source of truth** for a kanban board. A change from the board goes through `commit()` → `serializeBoard()` → `MarkdownView.replaceText()` so that it becomes one undo step.
- **Highlighting is deferred** with `GLib.idle_add(PRIORITY_HIGH_IDLE)` (`queueHighlight`, `queueCursorUpdate`). Do not call `highlight()` directly from a handler that can fire in succession.
- **Replacing the whole contents of a TextView that can be long** must go through `replaceAllText()` (`editor/view.ts`). Without it, GTK can lay out all the new lines at once on the first draw (on GTK 3 a 650 KB manuscript froze for ±0.6 seconds). That function only scrolls to the cursor if the TextView already has a size; a scroll that is queued before it is allocated is run by GTK 4 with empty geometry and opens the document in the middle/at the end. Do not change the `bottom_margin`/`top_margin` of the TextView at runtime: GTK then lays out the whole document again.
- **Incremental highlighting on opening:** after `setText()`, the tags of a long document (>200 lines) are done in installments in idle (`queueFill()`). A test that checks the tags at the end of a long document must wait for `ed.highlightComplete`; code that applies tags through `LineTagger` must respect the deferred lines (`defer()`/`fill()`).
- **Incrementally hidden markers:** `MarkerConcealer` (`editor/decorations.ts`) only checks the old/new active lines, the `reparsed` lines from the highlighter, and the lines that are not known yet. If you change the highlighter, make sure `reparsed` covers all the lines whose markers can change and the markers stay ordered by their lines; the test `incrementally hidden markers` in `tests/gui/robust.ts` guards that.
- **Write files through `files.ts`.** Autosave from the timer writes in the background (`writeTextFileAsync()`); a synchronous write, a move, and a delete of a file must call `flushWrites()` (already done by `writeTextFile()` and `fileops.ts`) so that the old contents do not overwrite the new.
- **Do not `remove_tag()` over the whole buffer and then apply it again.** GTK then lays out the whole document; that once made typing in a 30 KB document ±300 ms per keystroke. Use `setTagRanges()`/`setTagGroup()` or `LineTagger` from `editor/tagsync.ts`. A syntax tag must stay within one line (it may include its newline) so that `LineTagger` can be used.
- **Window width:** the editor's ScrolledWindow uses `hscrollbar_policy: EXTERNAL`, not `NEVER`, so that the window can shrink. The same applies to the ScrolledWindow in the Assistant panel (`ui/chat.ts`): with `NEVER`, a long text without spaces in the message box widens the panel; its test is in `tests/gui/chat.ts`. Do not call `set_value()` inside the `changed` signal of the panel adjustment (during allocation): the value changes but the viewport does not apply it, so the answer is shown cut off and the footer is not visible; `ChatPanel` scrolls through idle (`stickIdle`). `--shot-chat=<prefix>` saves a screenshot of the panel with a long answer.
- **Mermaid diagrams** are rendered by an invisible WebKitGTK (`editor/mermaidrender.ts`), loading `dist/mermaid.min.js` that is copied from `node_modules` by a plugin in `vite.config.ts`. Its layer (`editor/mermaid.ts`) uses its own `mermaidhide` tag; do not use it together with `tablehide` because every layer clears its tag across the whole buffer. A ```dbml block is translated into a Mermaid `erDiagram` by `markdown/dbml.ts` and uses the same layer. The first test that renders needs a few seconds (WebKit is started).
- **The Assistant:** the manuscript context is built in `agent/context.ts` (pure, tested in `tests/unit/agent.ts`); keep the `system` part stable between questions (the DeepSeek prefix cache) and everything that changes goes into `note`. The browsing tools of the model are in `agent/tools.ts` and are read-only; a new tool must be pure (working on top of `SourceFile[]`), must not throw, and must be registered in `TOOLS` and in `runTool()`/`describeCall()`. A tool that changes something must not go into `TOOLS`: it lives in `agent/changes.ts` (`CHANGE_TOOLS`), only produces a pure `Change`, and is run by the session through `onProposal`, which waits for the user's decision in the `ui/proposalviewer.ts` window (opened from the panel's card, `ChatPanel.review()`; the diff view is shared with `ui/historyviewer.ts`); its application (`applyChange()` in `app/agentwrites.ts`) must check again that the contents of the file have not changed and that its file name is safe. The Assistant lives in the application layer: `AppSession` owns it (`app/assistant.ts`, which owns the `ChatController` and builds its host from the session's documents, workspace, agent writes, and git), and `ui/chat.ts` is only a view (`ChatPanelView`, plain data in, `on*` actions out). A proposal is an ask: the panel gets the changes as data, asks the core to write them with `onApply(ask, chosen)`, and answers with its note; the result the agent sees is what the core wrote, never what the panel claims, and an apply after the turn was stopped is refused. Keep the panel from writing a file or holding a callback over the changes. A new write tool follows the same pattern and gets tests in `tests/unit/changes.ts` and `tests/gui/chat.ts`. The plan is in `agent/work.ts`, the verification in `agent/verification.ts`, the journal in `agent/journal.ts`, and recovery in `agent/recovery.ts`. A batch uses `onBatchProposal`, a preflight of the whole snapshot, and a rollback; writing in the window checks symlinks with `agent/path.ts`. The agent loop is in `agent/session.ts`. Tests must not call the real API: use a fake `Provider` (`w.session.assistant.chat.makeProvider`) and a fake `KeyStore` (`…chat.keyStore`); the Assistant without GTK, with a recording panel, is tested in `tests/unit/assistant.ts`; `systemKeyStore` touches the keyring and the files in `~/.config`. libsoup and libsecret are loaded with a dynamic `import()` so that a missing typelib does not kill the app. A core test that waits for a Promise is `async` and awaits `within()` (or polls with `until()`) from `tests/framework.ts`, so it also runs on Node; only a GUI test uses `settle()`, which spins a nested GLib main loop.
- **Many documents (tabs):** `MainWindow` holds `docs: Doc[]` and one active `doc`; `w.editor` and `w.file` are getters to the active document, so do not keep `w.editor` in a long-lived variable (the tests use `c.ed` only while the first tab is active). An editor callback must check `doc === this.doc` before touching the shared components (the outline, the status bar). `load()` replaces the contents of the active document; `openInTab()`/`openFile()`/`newDocument()` open a tab (a document without a file and without changes is reused). A test that opens a file through the tree or `newDocument()` must close its extra tab (`w.closeTab()`) so that the `ed`/`buf` of the context stay the active document. Closing an editor destroys its widgets: an idle/timeout in the editor layers must check the `destroyed` flag, otherwise `Gjs-CRITICAL ... already disposed` appears.
- **The external harness:** a card with `[agent:: pi]` is run by `orchestrator.ts` in the project folder that is mapped from the name in `settings.projects` (only filled in through the choose-folder dialog; do not accept a path from the Markdown contents or from the agent), and `checkProjectFolder()` rejects the Markwork work folder together with its contents/parents. The pure logic (the prompt, `PiReader`, `RunQueue`) is in `agent/harness.ts` and tested in `tests/unit/harness.ts`; the GUI test (`tests/gui/harness.ts`) uses a fake pi script through `w.harness.orchestrator.program` and `w.harness.dialogs`, never the real pi. Pi is run in RPC mode: commands (prompt, `steer`, `extension_ui_response`) are written to stdin as one line of JSON, and a run has the status `waiting` while it waits for the user's answer (it still holds the queue of its folder). Read and write the process pipes with `GLib.IOChannel` like `spawnHarness()`: `Gio.Subprocess.get_stdout_pipe()` after Gtk is loaded triggers the Gjs-WARNING `Gio.UnixInputStream has been moved`, and `write_chars()` must be given bytes with an explicit length (a string with length -1 triggers the GLib-WARNING `Invalid UTF-8`). The fake pi in the tests is a shell script that reads stdin; use `printf '%s\n'`, not `echo`, for JSON lines that contain `\n` (the dash echo interprets them).
- **Conversation history:** `ChatController.persist()` (`agent/chatcontroller.ts`) writes to `<folder>/.markwork/chats` through `agent/chatstore.ts` (the format is in `agent/transcript.ts`, including work checkpoints and the action journal; tested in `tests/unit/transcript.ts`, `work.ts`, and `agentic.ts`). The GUI tests use a temporary folder, so it is safe; do not write to the user's folders. Dot folders are still not read by `WorkspaceRepository` (`workspace.ts`), keep that so that the assistant does not browse its own history.
- **An async callback can be lost.** GJS 1.80 blocks a JS callback that arrives during garbage collection (`Gjs-CRITICAL: Attempting to run a JS callback during garbage collection … blocked`, see `bench/GC-DIAGNOSIS.md`); the operation finished, but its callback never runs. Anything an agent tool or a user waits on must have an end that does not depend on that callback: `runGit()` (`git.ts`) has a watchdog that turns a lost result (git exited, no callback after `gitLimits.lostMs`) or a hanging git (`gitLimits.runMs`) into an ordinary failure, without repeating the command (it may have been a commit). A new long-lived subprocess or async wait follows the same idea; its test can replace the async method on the prototype with one that never calls back.
- **GTK 4 through GJS does not emit `destroy` for a widget that JavaScript still holds.** Do not use that signal to clean up timers/idles. A component that has timers provides its own `destroy()`; `MainWindow.dispose()` (from the window's `unrealize` signal) and `closeTab()` call it. A child window uses `unrealize` to mark itself closed.
- **A modal dialog returns a Promise**, without a nested main loop (`modal()` in `gtkutil.ts`): `Gtk.FileDialog` for files, `modalWindow()`/`alert()` (`ui/dialogs.ts`) for forms and messages. Do not add a `GLib.MainLoop` to the app code to wait for a dialog. The caller continues with `after(value, continuation)` and the type `Awaitable<T>`, so the path without a question and the dialog fakes in tests (which return a plain value) stay synchronous; a continuation after a dialog must check the state again (the tab/card still exists). A test that uses a real dialog waits with `settle(promise)` while scheduling clicks from a timer. Do not use `Gtk.AlertDialog` or `destroy_with_parent` (a GLib-CRITICAL when the process exits). A dialog must still be replaceable in tests. `Gtk.FileDialog` uses xdg-desktop-portal if it is on the session D-Bus: run a manual test script that opens a file dialog with `dbus-run-session` and `GDK_DEBUG=no-portals` so that the dialog does not appear on the user's desktop.
- **Git history:** `app/history.ts` (`HistoryController`, owned by `AppSession` as `session.history`) runs git through `git.ts` and the commit message writer; `ui/history.ts` (`HistoryTabView`) and `ui/historyviewer.ts` (`HistoryViewers`, implementing `HistoryViewersView`; a viewer is named by a number) only draw plain data and report through `on*` actions, and must not import `git.ts` for its values again. The discard question is `HistoryDialogs.discard` (a test replaces `w.session.history.dialogs.discard`); an open document takes the restored file through `editor.update()`. Tests: `tests/unit/history.ts` (no GTK, real git, a `LaggingEditor` discard; each test awaits `history.settled()` before `session.dispose()`: git reads left running from the core tests answered during the GUI tests' GC on GJS and left GJS refusing every later callback, thousands of `Gjs-CRITICAL … sweeping phase of GC` and a `GtkPopover is not a child` flood at exit) and `tests/gui/history.ts` (`--only-history`; `--shot-commit=<prefix>` saves the commit form and the viewer).
- **`hexpand`/`vexpand` are propagated upward in GTK 4.** The side panels (the sidebar, the History/Files tabs, the Assistant panel) are given an explicit `hexpand: false`; if you add an expanding widget inside them, make sure the test `the history tab does not make the sidebar expand` keeps passing.
- **The selection must never be empty for a moment** when a format command changes the selected text: on X11 GTK 4 then drops the new selection (the PRIMARY clipboard). Insert/delete at the edge of the selection, do not delete and then insert again (see `wrapSelection()`).
- **The file tree (TreeListModel + ListView):** `ui/filetree.ts` is the view of `FilesController` (`app/files.ts`, owned by `AppSession` as `session.files`, which also answers `root()` for every controller): the controller lists and watches folders through the port and runs the file operations with `FilesDialogs` (a test fills `w.session.files.dialogs`); the tree draws what `showRoot()`/`showFolder()` send and reports through its `on*` actions. The `create_func` of the TreeListModel is also called just to check whether a row can be expanded, so a folder's store is kept in `dirStores` and its contents asked for once (`onOpenFolder`). The position of a row is read from `pick()` + `TreeExpander.get_list_row()`. Do not use a widget as a drag icon (`GtkDragIcon` → Gtk-CRITICAL); use `DragSource.set_icon()`.
- **New UI follows the GNOME idioms:** use libadwaita widgets (`Adw.*`) and the default style classes (`navigation-sidebar`, `dim-label`, `card`) before adding CSS; a static layout is written in a `.ui` file (`Gtk.Template`, see `ui/preferences.ts`), not a chain of `new Gtk.Box()`; lists use `Gio.ListStore` + `Gtk.ListView`; a new command is added to `COMMANDS` in `app/commands.ts` (id, label for the palette Ctrl+Shift+P, default keys as `Ctrl+Shift+P`, scope, and a `run` through `CommandHost`; a new operation becomes a `CommandHost` method that `MainWindow` implements) and `actions.ts` registers it as a `Gio.Action`; a new preference is added to `data/com.ekaput.Markwork.gschema.xml`, `AppSettings`, and `ui/preferences.ui`. `Adw.HeaderBar`/other final classes cannot be subclassed; wrap them with `Adw.Bin`. A secondary window uses `Adw.Window` + `Adw.ToolbarView`, not a `Gtk.Window` with `set_titlebar()`. Interface colors use the named Adwaita colors (`@accent_color`, `@card_bg_color`, `@error_bg_color`, ...) in `ui/theme.ts`; hex values only for the document surfaces (text tags, tables, diagrams). The installed libadwaita is 1.5 (GTK 4.14): newer APIs (`Adw.ShortcutsDialog` 1.8, the system accent 1.6, `AdwSidebar` 1.9, GTK 4.20 CSS media queries) may only be used with feature detection and a tested fallback path, like `ui/shortcuts.ts` and `withSystemAccent()`. Do not use a widget that is deprecated in newer GTK if there is a replacement in 1.5/4.14 (e.g. `GtkComboBoxText` → `Gtk.DropDown`, `Gtk.ShortcutsWindow` → `Adw.Dialog`, `Gtk.Picture.new_for_pixbuf` → a texture).
- **Interface text must be translatable.** Wrap it with `_()` from `src/i18n.ts`; text with values uses `fmt(_('… {name} …'), { name })`, not a template literal (xgettext cannot extract it); an ambiguous word uses `pgettext(context, text)`. In `.ui` files, give `translatable="yes"`. A new file that holds interface text is added to `po/POTFILES.in`; check with `npm run pot`. Text read by the model (prompts, tool descriptions, tool results in `agent/`) and the contents of documents are not translated.
- **Adaptive layout:** an `Adw.Breakpoint` in `MainWindow.addBreakpoints()` folds the panels in a narrow window, and `bindPanel()` keeps the GSettings of a panel from being overwritten by the automatic fold. A new side panel uses the same pattern; the test `a narrow window collapses the Assistant panel…` (`tests/gui/gnome.ts`, `--shot-gnome=<prefix>` for a screenshot) guards it.
- **Workbench formats (Home, Inbox, Journal, `[[note]]` links):** An item (kanban card or inbox note) carries typed fields as `[key:: value]` in its first line (`due`, `agent`, `created`; `#tag` is the only other marker); `markdown/fields.ts` parses and writes them, `kanban.ts` and `inbox.ts` build their card and note functions on it (`kanban.ts` holds the one model of a board and of a list: groups of notes, the unnamed group before the first `##` always first; `layout.ts` reads the `layout:` line, `ui/inbox.ts` is the view of `layout: list`, and `ui/table.ts` with `markdown/tablelayout.ts` (columns, sort, rows; pure) is the view of `layout: table`), and its parser never rejects or rewrites text it does not understand. each is a pure model in `markdown/` (`home.ts`, `inbox.ts`, `journal.ts`, `wikilink.ts`, tested in `tests/unit/`) plus a view or window code that only draws it. An inbox is a document with `layout: list` frontmatter shown by `ui/inbox.ts`; like the kanban board, every change goes through `commit()` → `onChange` → the buffer, so the Markdown text stays the single source of truth. Home (`ui/home.ts`) does not read files itself: `window/home.ts` recomputes its data from the files every time it is shown, without an index; boards and inboxes are read through `workspace.files(root, { keep })` so the `keep` filter applies before the 300-file limit (`f74d5b5`). The journal is `journal/YYYY-MM-DD.md`; activity (cards moved/checked/added, applied agent changes, harness results) is appended to `.markwork/activity/YYYY-MM-DD.jsonl` by `activity.ts` (a failed write is swallowed, never breaks the work that triggered it) and merged into the *Activity* section only by adding lines that are not there yet, so user edits are never overwritten; keep that rule. Section titles of the journal are document content and are not translated. `[[note]]` targets are resolved by file name without extension, case-insensitively, against Markdown files of the work folder (`folder/Note` matches the end of the path); the `[[` suggestion popover (`editor/wikicomplete.ts`) never takes focus, `MarkdownView.onKey` forwards arrows/Enter/Tab/Esc to it, and it asks the window for the note list through `listNotes` because the editor knows nothing about folders. Links inside table cells use the `markwork-note:` URI scheme on `activate-link`.
- **The file tree shows Markdown and image files** (`isMarkdownFile()`/`isImageFile()` and `listFolder()` in `app/files.ts`); activating an image opens the `ImageViewer` window, not an editor tab. A new file kind added to the tree must decide where it opens in `window.ts`.
- **Context menus** are written as a `MenuEntry[]` (`ui/menu.ts`) and shown with `popupMenu()`; a test calls the `run()` of its entry.
- **Tests on Xvfb (a 1280×800 screen):** do not let a test window be wider than the screen. A popover from a button outside the monitor triggers a `gdk_monitor_get_geometry` Gdk-CRITICAL on GTK 4/X11; restore the window size (e.g. 1100×700) after a test that enlarges it.
- GJS has no HMR; a change is only visible after the app is reopened (`npm run dev` does it automatically).

## Adding or changing a feature

1. A new Markdown rule → put it in `src/markdown/` (without GTK) and write a test in `tests/unit/`.
2. Editor/UI behavior → a GUI test in `tests/gui/`. Every test module exports one function. A test of the core (no GI) is registered in `tests/core-tests.ts`, which runs under GJS (`npm test`) and on Node (`npm run test:core:node`); it reaches the runtime only through `platform()` and `host()` (`tests/host.ts`; `disk` in `framework.ts` for test files), never `gi://`. A unit test that needs GI and the GUI tests are registered in `tests/run-tests.ts` (`runUnitTests` or `runGuiTests`). Use `section`, `test`, `eq`, `ok` from `tests/framework.ts`; a test that waits is `await test(name, async () => …)`.
3. A new Markdown format → add its example to `tests/samples/all-formats.md` (used by the tests and the HTML export).
4. A dialog that holds up the program (modal) must be replaceable in tests, like `KanbanBoard.dialogs`.
5. A changed feature, shortcut, or folder structure → update `README.md` (the shortcut table, the feature list, the folder tree, and the related "How it works" section) and the menus/actions in `actions.ts`/`headerbar.ts`.

## The test environment

- Tests use `AppSettings.inMemory()` (the in-memory GSettings backend), so the user's dconf is not touched, and temporary folders for files. Do not write to the user's home or make a `new AppSettings()` (the real dconf) from a test.
- `--only-dialogs`, `--only-chat`, and `--only-folder-mouse` (together with `--with-kanban-mouse`) run part of the tests for fast iteration.
- `--mouse` moves the real pointer through XTest; run it only if asked.
- `npm test` automatically includes the kanban mouse tests on Xvfb. `npm run docs` still uses the desktop display as before.
- `npm run test:ui` shows all the tests, including mouse drags, on the desktop; run it only if the user asks for the displayed test mode.
- Do not edit `dist/` or `node_modules/` by hand.

## Git

- Commit messages are in English, one short sentence in an imperative/descriptive form, written as `type(module): description` (e.g. `fix(dialogs): handle the delete confirmation when there is no extra detail`). `type` is one of `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`; `module` is the area changed, such as `filetree`, `editor`, `kanban`, `assistant`, `home`, `journal`, `build`, or `docs`.
- One logical change per commit; include its tests in the same commit.
